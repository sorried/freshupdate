# freshGram updates notify

независимый telegram-бот для уведомлений о новых релизах [freshGram](https://github.com/Snowy-Fluffy/freshGram). запуск бота в личном чате включает уведомления, без подписки на каналы и дополнительных проверок.

бот: [@freshupdbot](https://t.me/freshupdbot). идентичность подтверждена через telegram `getMe`, id бота `8754181443`. это не подтверждает, что production-процесс уже запущен.

independent telegram release notifications for freshGram, built with typescript, grammY and sqlite.

## возможности

- ровно две команды: `/start` и `/about`;
- стабильные и предварительные релизы, с возможностью отключить предварительные;
- автоматическая проверка github каждые 300 секунд;
- уведомления с названием, версией, датой utc, кратким описанием и кнопками;
- каомодзи вместо обычных эмодзи, экранирование внешнего текста и ограничение длины;
- sqlite для пользователей, релизов, очереди рассылки и антиспама;
- восстановление очереди и блокировок после рестарта;
- etag для каждой страницы github api, ограниченные повторы и соблюдение rate limit;
- node.js-запуск на linux/vps и docker compose без внешней базы данных;
- typescript с `strict: true`, grammY, better-sqlite3 и встроенный `fetch`.

## команды

`/start` открывает приветствие с кнопками исходного проекта, всех релизов и информации. повторный запуск обновляет запись пользователя, не создавая дубль.

`/about` рассказывает о freshGram и этом боте. первое обращение также включает уведомления. кнопка информации использует ту же логику и антиспам-счётчик, что `/about`.

бот работает только в личных чатах. других пользовательских команд нет. чтобы перестать получать сообщения, можно заблокировать бота средствами telegram. после повторного `/start` или `/about` запись снова становится активной.

### проверка владельцем

владелец с telegram id `994782321` может отправить ровно `@test_send` обычным текстом в личном чате. бот получит свежие данные github и отправит владельцу тестовое уведомление о последнем опубликованном релизе. очередь и состояние отслеживания не меняются, остальные пользователи ничего не получают. триггер не добавляется в меню команд и не работает у других пользователей или в группах. он использует антиспам-счётчик `/about` и соблюдает jail.

### сообщения об ошибках

ошибки обработки обновлений, github, доставки и запуска отправляются только владельцу `994782321`. обычному пользователю при ошибке его запроса приходит только `(╥﹏╥) что-то пошло не так. попробуй немного позже.`. фоновые ошибки не рассылаются подписчикам. технические детали не включаются в пользовательские ответы.

отчёты владельцу содержат тип и описание ошибки, а для внутренних ошибок также stack trace. токены маскируются, telegram payload и вложенные сетевые исключения не пересылаются. одинаковое направление ошибок уведомляет не чаще одного раза в пять минут в пределах процесса, чтобы массовая ошибка доставки не засыпала владельца сообщениями. ошибка самого уведомления не вызывает рекурсивных сообщений. владелец должен предварительно запустить бота и не блокировать его. без рабочего токена, сети или telegram api доставить отчёт невозможно, в таком случае остаётся безопасная запись в журнале. при отсутствии токена приложение выводит ошибку локально.

## как отслеживаются релизы

источник: `https://api.github.com/repos/Snowy-Fluffy/freshGram/releases?per_page=100`. приложение обходит следующие страницы, не ограничиваясь первыми 100 релизами. черновики пропускаются. уникальный ключ релиза - github release id.

при первом успешном полном запросе опубликованные релизы сохраняются как исходное состояние. старые версии не рассылаются. ошибка api не создаёт исходное состояние и не означает отсутствие релизов. пустой json-массив является допустимым ответом; пустое тело или некорректный json являются ошибкой.

новые релизы сохраняются вместе с очередью для активных пользователей одной транзакцией. порядок - дата публикации, затем id. для каждого адресата более поздний релиз ждёт завершения предыдущего. новые пользователи не получают уже поставленные в очередь релизы. изменение названия или описания существующего release id не вызывает повторной рассылки.

при `INCLUDE_PRERELEASES=false` предварительные релизы всё равно отмечаются просмотренными, но не рассылаются. последующее включение не отправляет их задним числом. переключение `GITHUB_REPOSITORY` требует отдельного файла базы, чтобы не смешивать release id разных репозиториев.

сеть и серверные ошибки github повторяются не более трёх раз за цикл, с задержками 1 и 2 секунды. при http 403/429 приложение переносит следующий цикл, учитывая `Retry-After` или `X-RateLimit-Reset`. после повторяющихся ошибок задержка возрастает. etag и содержимое страниц сохраняются в sqlite только после успешного полного обхода.

рассылка ограничена примерно 20 сообщениями в секунду. telegram flood limit приостанавливает всю очередь, срок паузы сохраняется в базе. временные ошибки имеют экспоненциальную задержку и максимум пять попыток на доставку. окончательные ошибки отмечаются `failed`, заблокировавшие бота пользователи становятся неактивными. их записи не удаляются.

абсолютной гарантии exactly-once нет: если telegram принял сообщение, а процесс завершился до сохранения `sent`, после рестарта возможен дубль. уникальный ключ `(release_id, user_id)` предотвращает обычное повторное создание доставки. сбой до отправки также расходует попытку, поэтому постоянные сбои могут привести к `failed`. приложение не повторяет доставку бесконечно.

если релиз появился и был удалён на github целиком между проверками, бот не сможет его обнаружить. изменение данных во время многостраничного запроса может сдвинуть обнаружение до следующего цикла.

## антиспам и jail

четвёртый вызов одной и той же команды в скользящем окне 60 секунд блокирует команды на 300 секунд. `/start` и `/about` считаются отдельно. три вызова разрешены. событие ровно 60 секунд назад уже не входит в окно.

бот один раз пытается отправить уведомление о конкретной блокировке, затем молча игнорирует команды до её окончания. кнопка информации также считается вызовом `/about`. во время jail фоновые уведомления о релизах продолжаются. блокировка переживает рестарт; устаревшие события регулярно очищаются.

решение о блокировке принимается через `BEGIN IMMEDIATE` в sqlite. параллельные обращения не создают несколько уведомлений. доставка самого предупреждения не гарантируется: при сетевом сбое или остановке между сохранением jail и отправкой предупреждение не повторяется, чтобы не спамить пользователю.

это защита от спама командами на уровне приложения, не сетевая ddos-защита. защита vps от сетевых атак требует мер хостинга, провайдера, сетевых фильтров и инфраструктуры.

## быстрый запуск на linux

нужны node.js 22+, npm, git и доступ по https к github и telegram. ci проверяет node.js 22, 24 и 26. токен существующего бота получите через botfather. не публикуйте его в issue, логах или git.

пока изменения проходят ревью, используйте ветку `dev`:

```bash
git clone -b dev https://github.com/sorried/freshupdate.git
cd freshupdate
npm ci --ignore-scripts
npm run build
cp .env.example .env
chmod 600 .env
```

заполните `BOT_TOKEN` в `.env`, затем:

```bash
npm start
```

можно запускать напрямую `node dist/main.js`. запускать нужно из каталога проекта, чтобы `.env` и относительный `DATABASE_PATH` разрешались предсказуемо. `.env` загружается встроенным `process.loadEnvFile`, отдельная зависимость не нужна. при отсутствии или явно неправильном токене приложение завершается с понятным сообщением без stack trace. better-sqlite3 13 поставляет готовые native-бинарники для поддерживаемых платформ; docker использует debian linux. на неподдерживаемой платформе потребуется отдельная сборка native-модуля.

при запуске выполняется telegram `getMe`, в журнал выводятся только подтверждённые username и id самого бота. id бота не используется как id подписчика. локальный токен проверен и соответствует `@freshupdbot`; после замены токена приложение проверяет идентичность заново. приложение не создаёт нового бота и не меняет профиль автоматически.

если установлен webhook, приложение прекращает запуск, не удаляя его самостоятельно. отключите старый webhook через bot api `deleteWebhook`, сохраняя ожидающие обновления. имя и описание можно настроить через botfather владельцем бота. проверьте, что старые индивидуальные или языковые меню команд удалены: приложение регистрирует только `start` и `about` в стандартном меню.

### постоянный запуск на vps

запускайте от отдельного непривилегированного пользователя. пример `deploy/freshupdate.service` рассчитан на каталог `/opt/freshupdate` и системного пользователя `freshupdate`. сначала установите проект, создайте каталог `data/` и заполните защищённый `.env` в этом каталоге. пользователь сервиса должен иметь право записи в `data/`.

```bash
sudo install -m 644 deploy/freshupdate.service /etc/systemd/system/freshupdate.service
sudo systemctl daemon-reload
sudo systemctl enable --now freshupdate
sudo journalctl -u freshupdate -f
```

файл сервиса - пример для установки, не признак уже выполненного развёртывания. он ожидает node.js в `/usr/bin/node`, при другом пути измените `ExecStart`. приложение останавливает polling, отменяет запросы и фоновые задачи через `AbortSignal`, затем закрывает sqlite при sigterm. аренда экземпляра в sqlite запрещает второй процесс с той же базой. срок аренды 120 секунд, обновление каждые 30 секунд. после аварийного завершения новый процесс может потребовать до двух минут ожидания. не запускайте несколько экземпляров с одним токеном и разными базами: telegram polling и рассылки будут конфликтовать.

## docker compose

нужны docker engine и плагин docker compose. создайте и заполните `.env`, как описано выше.

```bash
docker compose up -d --build
docker compose logs -f bot
docker compose stop
```

контейнер запускается не от root, с read-only файловой системой и автоматическим перезапуском. named volume `bot-data` хранит sqlite в `/app/data/bot.db`. `DATABASE_PATH` внутри compose намеренно фиксирован, чтобы база не попала во временный слой контейнера. опубликованных портов нет, используется long polling.

volume сохраняется при пересоздании контейнера и обычном `docker compose down`. не используйте `docker compose down -v`, если данные нужны: эта команда удаляет volume. делайте резервные копии через sqlite backup api или после остановки процесса. не копируйте только `bot.db` во время работы без учёта wal.

## конфигурация

| переменная | значение по умолчанию | назначение |
|---|---|---|
| `BOT_TOKEN` | отсутствует | обязательный секрет telegram bot api |
| `GITHUB_REPOSITORY` | `Snowy-Fluffy/freshGram` | публичный репозиторий `owner/name` |
| `CHECK_INTERVAL_SECONDS` | `300` | положительное целое число секунд |
| `INCLUDE_PRERELEASES` | `true` | только `true` или `false` |
| `DATABASE_PATH` | `data/bot.db` | постоянный файл sqlite |
| `GITHUB_TOKEN` | отсутствует | необязательный github-токен для увеличения лимита api |

переменные окружения имеют приоритет перед `.env`. github-токен не нужен для публичного репозитория. не устанавливайте интервал в одну секунду в production: это быстро исчерпает api rate limit.

## безопасность и данные

в базе хранятся telegram id, первое и последнее обращение, флаг активности, срок jail и временные события команд. username, имя, телефон и текст пользовательских сообщений не сохраняются. дополнительно хранятся публичные релизы, etag, состояние доставки и число попыток.

telegram id нужен только для отправки уведомлений. пользовательский интерфейс не раскрывает чужие id. приложение не пишет id пользователей или секреты в журналы; ошибки внешних api журналируются без тела ответа. файл базы и `.env` содержат чувствительные данные, доступ к ним должен быть только у владельца процесса. процесс устанавливает umask `077`; права существующих файлов нужно проверить отдельно.

sqlite использует параметризованные запросы, wal, foreign keys и `synchronous=FULL`. база должна находиться на локальном постоянном диске, не на сетевой файловой системе. синхронные операции sqlite подходят для небольшого бота; при большой аудитории или длинных транзакциях потребуется отдельно измерить задержки и пересмотреть работу очереди.

внешний текст github не исполняется. html экранируется, описание показывается как обычный текст, без интерпретации markdown. разрешены ссылки конкретного github-репозитория. обычные эмодзи из описаний убираются; полное оригинальное описание доступно по ссылке.

`.env`, базы, окружение, кэш, ключи и локальные логи исключены из git и docker build context. зависимости закреплены в `package.json` и `package-lock.json`, установка выполняется через `npm ci`. lifecycle-скрипты зависимостей отключены. docker-образ и github actions закреплены по digest и commit sha. обновляйте их после проверки исправлений безопасности.

## разработка

```bash
npm ci --ignore-scripts
npm run check
npm audit
```

тесты используют временную sqlite и моки внешних api, не требуют `BOT_TOKEN` и не отправляют сообщения. проверяются регистрация, исходное состояние, очередь, etag, ошибки api, безопасный текст, лимиты доставки, sliding window, рестарты и параллельные транзакции.

`npm run check` запускает строгую типизацию, biome, проверку исходников, typescript-тесты через встроенный `node:test` и production-сборку. отдельно доступны `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` и `npm run format`.

`scripts/check-source.mjs` проверяет отсутствие комментариев, включая jsdoc, и случайных секретов в коде и конфигурации. readme и самостоятельная документация могут содержать пояснения. ci выполняет полный набор проверок на node.js 22, 24 и 26, проверяет production-зависимости через `npm audit` и собирает docker при push в `dev` и pull request в `main`.

при обновлении зависимостей меняйте закреплённые версии и lock вместе, затем повторяйте проверки:

```bash
npm install --save-exact grammy@1.46.0 better-sqlite3@13.0.3 --ignore-scripts
npm run check
npm audit
```

структура приложения: `config`, `database`, `github`, `tracker`, `handlers`, `antispam`, `messages`, `delivery`, `runtime` и `main`. `telegram-signal` согласует native `AbortSignal` с устаревшим типом сигнала в grammY, без `any` и дополнительной зависимости. изменения публикуются в `dev` логическими коммитами. pull request в `main` остаётся открытым до явного подтверждения владельца.

## переход с python-версии

остановите старый процесс, сделайте резервную копию sqlite и обновите приложение. путь `DATABASE_PATH` и docker volume должны остаться прежними. схема таблиц, json-поля релизов и время в секундах совместимы с python-версией: пользователи, история релизов, незавершённые доставки и jail сохраняются. повторная инициализация старых релизов не выполняется.

docker-пользователь node имеет uid 1000, старая версия использовала uid 10001. для существующего volume после остановки старого контейнера нужно один раз изменить владельца:

```bash
docker compose build
docker compose run --rm --no-deps --user root --cap-add CHOWN bot chown -R node:node /app/data
docker compose up -d
```

не удаляйте volume и не запускайте старую и новую версии одновременно. python-код и зависимости больше не нужны; старое локальное виртуальное окружение можно удалить самостоятельно после успешного перехода.
